[v2-followup.md](v2-followup.md), 복원 기록은 [v2-restoration.md](v2-restoration.md), 다이어그램은

## 1. 운영 점검 항목 6개 (2026-09-11)

| # | 항목 | 결정 | 근거 |
|---|---|---|---|
| 1 | DRM/COM 프로세스 격리 + 타임아웃 | **추가 안 함 — 이미 있음** | `kg/v2/jobs.py`: Reader는 종류와 무관하게 `multiprocessing` spawn 프로세스에서 실행, `KG_V2_READER_TIMEOUT_SECONDS`(기본 120초) 초과 시 프로세스 종료·`READER_TIMEOUT`, POSIX `RLIMIT_AS`(`KG_V2_READER_MEMORY_MB`, 기본 1,536MB), IPC 이벤트 8MB 상한. COM Reader는 운영자 factory가 그 프로세스 안에서 만들면 같은 격리를 받는다(Windows는 RLIMIT이 없어 메모리 제한은 제공자 몫 — runtime 문서에 명시). |
| 2 | SQLite WAL | **추가 안 함 — 이미 있음** | `kg/v2/db.py`: 연결마다 `journal_mode=WAL`, `foreign_keys=ON`, `busy_timeout=5000`. 설계 §10의 "로컬 디스크 전제·단일 writer 큐" 그대로. (v1 `kg/store.py`는 busy_timeout만 있으나 v1은 유지보수 모드라 손대지 않음.) |
| 3 | DKG(문서군) 캐시 | **추가함** | 실측 `GET /kg/{id}/graph`: 200문서·700 series 10.5ms, 2,000문서·10,000 series·1,220노드 **96ms**(첫 호출 300ms). 개념 탐색 화면이 탭 진입마다 호출하므로 문서가 수천 건이면 체감된다. 조치 3가지 — (a) 커버리지 쿼리를 "발행된 적용 건" 기준으로 재작성(결과 동일, 3.6배 빠름), (b) `document(current_version_id,document_id)` 인덱스(플래너가 자동 인덱스를 만들던 자리), (c) **(문서의 현재 버전 목록, 적용 건의 발행 실행 목록)의 SHA-256을 서명으로 쓰는 프로세스 내 캐시**(리비전 16개). 실행·series·매핑이 불변이라 이 두 목록이 같으면 그래프도 같다 — 즉 서명이 정확한 무효화 조건이다(uuid의 max/count 같은 근사 서명은 재발행 시 놓칠 수 있어 채택하지 않음). 결과 96ms→4ms, 10.5ms→0.5ms. 테스트: 발행·새 버전 후 재계산 확인. |
| 4 | `data_payload` LEFT JOIN + `representative_values` 폴백 | **추가 안 함 — v2에 해당 없음** | `data_payload`·`representative_values`는 v1 자료구조(`kg/webapp.py`, `kg/groups.py`, `kg/search.py`)로, 트리 노드에 값이 없을 때 대표값으로 대체하던 장치다. v2는 값 저장이 `extracted_item`(불변) 하나이고 모든 항목이 `item_region`으로 원자 출처를 가진다(설계 §5). "값은 있는데 위치가 없다"는 상태가 스키마상 존재하지 않으므로 폴백이 성립하지 않는다. |
| 5 | 원본 화면 `data.sheets` 방어 | **v2는 이미 방어, v1만 한 줄 보강** | v2 `frontend/src/v2/Source.tsx`는 `sheets.data?.items`와 `<State>`로 로딩/실패/빈 상태를 처리한다. v1 `frontend/src/screens/SourceScreen.tsx:174`는 `data.sheets.map`이 무방비였고 `?v1=1`이 아직 서비스되므로 `(data.sheets ?? [])`로 고쳤다. 그 이상(v1 재설계)은 유지보수 모드 정책상 하지 않는다. |
| 6 | `.env` 자동 로드 | **추가함** | v1·v2 모두 `.env`를 읽지 않았고 `.env.sample`은 "export하여 사용"이라고만 적혀 있었다 → `KG_V2_READER_FACTORY` 같은 운영 값을 매번 export해야 했다. `kg/env.py`(의존성 없음): `<workspace>/.env` → `./.env` 순으로 읽고 **이미 export된 값은 덮어쓰지 않는다**(운영 환경 우선), 주석·따옴표·`export ` 접두 처리. `python -m kg.v2 *`와 `python -m kg.webapp` 진입점에 연결. python-dotenv를 쓰지 않은 이유: 의존성 하나를 늘릴 만큼의 기능이 아니고, 덮어쓰기 규칙을 명시적으로 고정하고 싶어서. |

## 2. 범위 결정 (2026-09-09 ~ 09-10)

| 항목 | 결정 | 근거 |
|---|---|---|
| 실제 DRM SDK 연동·네이티브 렌더 | **하지 않음** | 이 환경에 SDK·제공자 문맥이 없다. `python -m kg.v2.reader_probe`로 계약 점검만 가능하며, 일반 XLSX나 테스트 대역을 DRM PoC로 계산하지 않는다(runtime 문서). |
| PDF 프리뷰(v1 LibreOffice 경로) | **제외** | DRM 문서에는 적용 불가(LibreOffice가 암호화 파일을 열 수 없고 v2는 해제본 경로를 제거), 설계 §8이 PDF 픽셀 좌표→셀 역산을 금지. 원본 충실 보기는 네이티브 어댑터로 해결한다. 제품 책임자 확인. |
| KG 그래프 캔버스 | **추가** | v1의 핵심 탐색 도구가 v2에 없었음. v1 배치 알고리즘과 토큰을 그대로 이식하고 데이터만 v2 규칙(현재 버전·발행 실행·리비전 고정)으로 계산. 하위 개념 없는 L1도 hull로 그린다(L1만 있는 KG가 빈 캔버스가 되던 문제). |
| 그래프의 `NODE_CAP`(2,000) 절단을 문서 목록 `roots[]`에도 적용 | **하지 않음** | 목록은 페이지 범위 요약이라 절단이 필요 없고, 절단을 흉내 내면 목록이 그래프의 임의 절단선에 종속된다. 대신 문서에 "그래프가 `truncated`이면 목록이 그래프가 떨어뜨린 뿌리를 보여줄 수 있다"고 명시. |
| 문서군 루트 이름의 기준 KG 리비전 | **매핑이 고정된 리비전** (최신 리비전 아님) | 최신 리비전에서 이름을 읽으면 개념을 폐기·개명한 뒤 목록과 그래프 화면이 다른 이름을 보이고, 폐기된 이름을 문서군 라벨로 쓰게 된다(리뷰에서 재현). 한 문서가 여러 리비전에 걸치면 가장 최신의 고정 리비전 이름을 쓰되 (문서, 루트)당 한 행만 남긴다. |
| v1 → v2 마이그레이션 | **추가, 단 값은 옮기지 않음** | 문서·KG·템플릿·배정은 새 안정 ID로 옮기고 링크를 남긴다. v1 값(`parsed_source`·`payload_value`)은 원자 출처가 없어 발행 추출로 복사하지 않고 "재추출 대상"으로만 보고한다(설계 §12-4·5). 매핑은 전부 `proposed`(§4.10, 사람 재검수). IS_A는 레벨 차가 1일 때만 `parent_of`로 방향을 뒤집어 옮긴다. |
| 문서군 자동 제안 + 레시피 이식 | **추가, 이식 규칙은 항상 검수 대기** | v1의 "같은 양식 제안→레시피 이식"을 v2 모델(적용 건·매핑 리비전)로 재설계. 자동 승인은 §4.10 위반이므로 없다. 구조 서명은 라벨 규칙으로 제한(`structure-v2`) — 업무키·이름 같은 데이터 값이 섞이면 같은 양식·다른 데이터 문서가 서로 다르게 보이기 때문. 휴리스틱임을 문서에 명시. |
| 전처리 프리셋의 위치 | **빌드 시점 → 검수된 추출 규칙의 명시적 변환** | v1은 빌드할 때 정규화를 골랐지만, v2는 값의 정규화가 출처·리비전에 고정되어야 재현이 된다. 프리셋 이름이 아니라 연산 배열을 버전에 고정하므로 YAML이 바뀌어도 과거 추출 의미가 바뀌지 않는다(복원 기록 "전처리의 의미"). |
| 파일 분석 화면 | **v1 목록 표 + 행 클릭 드로어로 복귀** | v2의 카드 목록+세로 상세는 단일 문서 상세에 가까워 여러 문서를 훑는 v1의 용도를 잃었다(제품 책임자 지적). v1 컬럼 중 "매핑 노드·개념 매핑%"는 v2에 대응 개념이 없어 제외, "DRM/Viewer" 3종은 "접근" 하나로 통합. |
| `GET /documents` 요약을 전체 코퍼스가 아닌 페이지 범위에서 계산 | **페이지 범위** | 전체 CTE는 200문서·5,340리비전에서 370ms, 26,700리비전에서 2.1s로 문서 수에 비례해 늘었다. 페이지 범위 + 인덱스 기반 재작성으로 8ms/28ms. 정렬 키(`template`, `review`)만 인덱스 기반 서브쿼리로 정렬 SELECT에 남긴다. |
| `json_group_array(... ORDER BY)` 사용 | **하지 않음** | SQLite 3.44 전용 문법이라 구형 배포판에서 목록 API 전체가 실패한다. `rn`을 JSON 안에 넣고 파이썬에서 정렬. SQLite 하한(3.38: JSON·윈도우 함수·재귀 CTE)은 설계 §10에 명시, 런타임 가드는 두지 않았다(가드가 있으면 구버전에서 아예 기동이 막히므로 문서로만). |
| 문서 상세 드로어 | **모달** (`aria-modal`, 포커스 트랩, 형제 요소 `inert`) | 배경 클릭·Esc로 닫히는 UI가 스크린리더/키보드에는 비모달로 보이던 불일치. 비모달로 가려면 배경을 없애야 하는데 제품 책임자가 요구한 "행 클릭 상세"에는 모달이 맞다. |
| PostgreSQL DDL·AGE projection·DVC | **파일·스크립트는 추가, 런타임 검증은 안 함** | 실행 중인 PostgreSQL/AGE/DVC가 없다. pglast 문법 검증과 객체 집합 비교, YAML 구조 검사까지만 했고 문서에 "런타임 미검증"을 명시했다. |
| e2e의 Playwright 브라우저 버전 고정 | **`CHROMIUM_PATH`로 사전 설치 브라우저 허용** | Playwright 1.63이 요구하는 chromium(1243)과 환경의 1194가 달라 로컬에서 e2e가 못 돌았다. CI는 자체 설치를 유지하고 로컬만 경로 지정. |
| Vitest 기본 타임아웃 | **5초 → 30초** | 느린 컨테이너에서 컴포넌트 테스트 1개가 타임아웃으로만 실패했다(코드 결함 아님). |
| API 요청 본문 | **raw dict → Pydantic 모델** | "`/docs`가 계약의 기준"이라는 문서와 달리 요청 스키마가 비어 있었다. 모델화 후 필드 단위 422 메시지가 나오고 `request_key`·작업 `state` enum이 문서화된다. |
| 매핑 리비전 POST에서 `request_key` 제거 | **제거** | 리비전 쓰기는 `expected_seq` CAS가 멱등성을 이미 보장한다. 이중 키는 혼란만 준다. |
| 등록 후 서명 계산 실패·취소 | **등록은 유지, 서명만 실패/건너뜀으로 기록** | 서명은 파생 캐시일 뿐인데 그 실패가 이미 커밋된 문서 버전을 잃게 하면 안 된다(`sign` CLI·`POST /versions/{id}/signature`로 나중에 계산). |
| 등록 시 Reader 프로세스 3회 → 1회 | **`describe`가 권한·서명을 함께 반환** | 등록마다 0.44s → 0.16s. 옛 계약의 어댑터는 그대로 동작(필드가 없으면 예전 경로). |

## 2-1. 브랜치 병합 결정 (2026-09-11)

| 항목 | 결정 | 근거 |
|---|---|---|
| `codex/v2-kg-coverage`(이웃 탐색 그래프 + 문서 버전별 검수 커버리지) | **공존으로 편입** — 기본 그래프는 v1 문서군 hull 캔버스(`GET /kg/{kg}/graph`), codex 구현은 `이웃 탐색` 모드(`kg_view=explore`, `GET /kg/{kg}/explore`) | 두 구현이 같은 경로를 다른 계약으로 썼다. hull 캔버스는 제품 책임자가 요구·확인한 v1 기능이고, codex의 이웃 탐색은 큰 KG(페이지당 30개·관계 120개)와 "선택 문서 버전의 검수 상태" 표시라는 별개 가치가 있어 버리지 않았다. `/kg/{kg}/concepts/{cid}`, `/concepts/{cid}/mappings`, `/series?document_version_id`는 그대로 수용하고 상세 패널에 "선택 문서의 검수 규칙 → 검수 →" 목록을 합쳤다. e2e는 같은 서버 워크스페이스를 공유하므로 각 시나리오가 최초 KG 리비전에 고정한다(순서 의존 실패를 실측하고 수정). |
| DVC 중심 최소 스키마(`db/dvc/*`, `docs/design/db-schema-dvc-minimal.md`) | **설계 제안으로 보존, 런타임 전환은 하지 않음** | 12개 테이블로 줄이는 제안이며 문서 자체가 "기존 `kg/v2` 런타임과 테스트가 v2 테이블에 결합돼 있어 비교/마이그레이션 기준으로 남긴다"고 명시한다. 제안의 불변식 테스트(`tests/test_schema_dvc_minimal.py`)는 통과하며 v2와 충돌하지 않는다. 전환 여부는 DRM 원본을 DVC에 둘 수 있는지(설계 §10: 정책상 불가하면 manifest만)에 달려 있어 제품 결정이 필요하다. |

## 3. 하지 않은 것 중 "다음에 할 것"

- 실제 DRM 어댑터 PoC (SDK가 생기면 `reader_probe`부터), 겹친 템플릿 동시 overlay, 이미지/OCR 키 추출, Python 템플릿 실행기.
- PostgreSQL/AGE 런타임 검증, `dvc repro`.
- 그래프 캐시는 프로세스 내 메모리다. 서버 워커를 여러 개 두면 워커별로 따로 계산한다(정확성은 서명이 보장하므로 문제는 없고 효율만 떨어진다).
